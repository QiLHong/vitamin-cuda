# 从加法到激活：比较相似代码中的关键差异

[中文首页](../../README.md) · [入门教程](./入门教程.md) · [翻译进度](./翻译进度.md)

这篇新增导读比较已补中文注释的三个模块：[Elementwise](../../kernels/elementwise/readme.md)、[ReLU](../../kernels/relu/readme.md)、[Sigmoid](../../kernels/sigmoid/readme.md)。它们都是逐元素运算，但不能因此假设边界条件、参数和数值行为完全相同。

## 1. 相同的线程骨架，不同的数学任务

| 模块 | 数学目标 | CUDA 入口的数据参数 | 原 PyTorch 参考 |
| --- | --- | --- | --- |
| Elementwise | `c[i]=a[i]+b[i]` | 两个输入、一个输出 | `torch.add(out=c)` |
| ReLU | `b[i]=max(0,a[i])`，普通有限实数 | 一个输入、一个输出 | `torch.clamp(min=0,out=b)` |
| Sigmoid | `b[i]=1/(1+exp(-a[i]))` | 一个输入、一个输出 | `torch.sigmoid(out=b)` |

三个模块都按线性索引处理连续数据，因此二维张量可以按 `numel()` 看作一维数组。这里并没有实现 PyTorch 广播，也没有自动处理不同 dtype 或非连续步幅。

## 2. 同样叫 x2，边界却不同

Elementwise 的 x2 在读写前检查 `idx<N`，但一次访问两个 half，因此仍需要正偶数 N 和正确对齐。ReLU 的 x2 没有任何边界判断；Sigmoid 的 x2 检查一整对，但其单元素 `else` 没有检查当前线程的起点是否有效。

所以，相同的“FP16 两元素”标签不意味着相同的安全条件。这里采用的保守学习条件是：Elementwise x2 使用正偶数 N；ReLU/Sigmoid x2 使用 N 为 512 的正整数倍。所有条件还依赖同设备、同 dtype、连续、足够输出空间和正确对齐。

## 3. 必须分别回答两个问题

**问题 A：每一次读写都在有效范围内吗？** 这不仅包括写回，还包括放在判断前面的读取、整个向量组、最后一个块的多余线程。

**问题 B：每一个需要的输出都有线程负责吗？** 核函数即使完全不越界，也可能因为网格计算有误而漏算尾部。

用 ReLU/Sigmoid 的八元素打包版本做纸面推导：

```text
N = 2049，num = 8，每块 256 个线程
原公式第一步：N / num = 256（整数向下取整）
原公式第二步：(256 + 255) / 256 = 1 个块
线程 t = 0..255，每个线程起点 idx = 8*t
最后一个线程覆盖下标 2040..2047
下标 2048 没有对应线程
```

这说明核内的尾部 `if` 无法修复根本没有启动的线程。反过来，仅把块数向上取整，也不能自动修复核内无保护的宽读取。正确的通用实现需要两层一起设计；本分支只解释原状，不偷偷改动算法。

## 4. 字节布局不等于数值精度

`float4` 搬运四个 float 的存储宽度是 16 字节，`pack128` 也占 16 字节，并可用四组 half2 表示八个 half。类型重解释关注的是同一片存储如何被访问；`.half()` 则真正改变张量 dtype 和数值表示。

ReLU 主要做比较，Sigmoid 包含指数与倒数。FP16 计算中的多个中间舍入可能导致不同误差，所以不要将某个简单算子的严格阈值机械复制到其他算子。

## 5. 一个用于加载与结果检查的冒烟步骤

在仓库根目录运行下面的 Bash 命令。它使用 N=2048、独立分配的连续 CUDA 张量和有限输入，避开上述已识别的尾部条件；不会运行原文件 `__main__` 中的完整性能循环。**此文档步骤在本次环境中未执行，也不代替原测试或全面正确性验证。**

仍然需要 PyTorch、NumPy、FlashInfer、Ninja、nvcc 及兼容的编译器。`runpy` 会执行测试文件顶层的导入和 `load()`，并非仅仅读取文本。

```bash
python - <<'PY'
from pathlib import Path
import runpy
import torch

if not torch.cuda.is_available():
    raise RuntimeError('请先配置可用的 CUDA 环境')

references = {'relu': torch.relu, 'sigmoid': torch.sigmoid}
with torch.no_grad():
    for module, reference_op in references.items():
        path = Path('kernels') / module / 'test.py'
        if not path.is_file():
            raise FileNotFoundError('请从 vitamin-cuda 仓库根目录运行')
        lib = runpy.run_path(str(path.resolve()), run_name=f'smoke_{module}')['lib']
        for dtype in (torch.float32, torch.float16):
            # 有限、较小的正负输入；这不覆盖极值、NaN 或 Inf。
            raw = ((torch.arange(2048, device='cuda', dtype=torch.float32) % 33) - 16) / 4
            a = raw.to(dtype).contiguous()
            expected = reference_op(a)
            suffixes = [''] + (['_fp32x4'] if dtype == torch.float32 else
                               ['_fp16x2', '_fp16x8', '_fp16x8_packed'])
            for suffix in suffixes:
                # 以 NaN 初始化可以帮助发现“没有写过的输出”；不是在测试输入 NaN。
                out = torch.full_like(a, float('nan'))
                name = module + suffix
                getattr(lib, name)(a, out)
                torch.cuda.synchronize()
                if not torch.isfinite(out).all().item():
                    raise AssertionError(f'{name} 出现非有限输出或未写入元素')
                tolerance = 1e-5 if dtype == torch.float32 else 1e-3
                torch.testing.assert_close(out, expected, rtol=0, atol=tolerance, equal_nan=False)
                print(module, dtype, name, '冒烟结果通过')
PY
```

文档示例使用 `torch.testing.assert_close` 的绝对容差判据；原脚本使用严格 `<eps` 的最大绝对误差 `assert`，两者不应被描述成逐字相同的测试。原脚本的基准参数和阈值没有修改。

## 6. 读完应能回答什么？

看到一个新版本，先写下“每线程覆盖哪些下标”，再列出每一次读取与写入的保护条件；接着从 CPU 网格公式推导线程总数，确认尾部既不会越界也不会漏算。最后检查真实 dtype、首地址对齐和输出生命周期，而不是只看函数名里有没有 `packed`。

对性能的判断还需要真实设备测试。这里的纸面推导与静态一致性检查能帮助理解代码，但不能证明特定 GPU 上更快，也不能替代 Compute Sanitizer、数值边界测试和实际编译。

依据：三个模块的 CUDA 源码与测试脚本。通用机制参见 [CUDA 编程指南](https://docs.nvidia.com/cuda/cuda-programming-guide/) 和 [PyTorch 扩展文档](https://docs.pytorch.org/docs/stable/cpp_extension.html)。
