# CUDA 零基础入门：从看懂一个元素开始

[返回中文首页](../../README.md) · [术语对照](./术语表.md) · [逐元素加法实战](../../kernels/elementwise/readme.md)

这篇教程是新增教学材料，不是原作者文章的逐字翻译。目标是让你读懂本仓库真实代码，而不是另写一个与仓库无关的示例。当前已完成的源码中文化范围见 [翻译进度](./翻译进度.md)。

## 1. 需要先会什么？

掌握变量、数组、循环、函数与最基本的指针概念即可开始。如果主要使用 Python，把 `torch.Tensor` 理解为“带形状、类型、设备信息的数据容器”。暂时不懂模板、宏或汇编也没关系，先看普通的 `elementwise_add_kernel`，后面再回来理解包装层。

推荐先做三个纸面练习：长度 8 的数组合法下标是 0～7；二维行主序矩阵第 r 行、第 c 列的线性下标是 `r*列数+c`；一个 float 占 4 字节，四个 float 占 16 字节。很多 GPU 错误本质上就是索引、字节数或类型没有分清。

## 2. CPU 与 GPU 如何合作？

常见程序中，CPU 准备参数并发起任务，GPU 执行大量并行计算。把 CPU 想成分配工作的组织者，GPU 想成同时容纳许多工作单元的车间；这个类比帮助理解分工，但真实调度远比类比复杂。

本仓库的 PyTorch 扩展与手写 `cudaMalloc` 的独立示例不同：Python 端用 `torch.randn(..., device='cuda')` 等操作得到设备张量，C++ 包装取出它们的指针，CUDA 核函数读写这些地址。显存生命周期主要由 PyTorch 张量管理，不能照抄独立示例对这些指针调用 `cudaFree`。

一个完整过程可以写成：

```text
创建输入 CUDA 张量 -> 创建输出 CUDA 张量 -> 进入 C++ 包装
-> 配置线程块并启动 GPU 核函数 -> 在合适的位置等待结果 -> 检查输出
```

CPU 和 GPU 并不是使用同一套普通指针规则。不要把普通 CPU 数组地址传给这里期望设备地址的核函数；也不要在 CPU 上直接解引用设备显存指针。统一内存等机制是另外的进阶主题。

## 3. Thread、Block、Grid、Warp

**Thread（线程）**是一个逻辑执行者。最简单的加法实现中，每个线程负责一个数组元素。**Block（线程块）**包含一组线程，可以使用块内共享内存并在满足条件时做块级同步。**Grid（网格）**是这次启动的全部线程块。**Warp（线程束）**是 NVIDIA CUDA 中通常由 32 个线程组成的执行分组；它不是一个额外要在 `<<<>>>` 中手工创建的层次。

启动很多逻辑线程不代表它们全在同一时刻执行。硬件会根据资源与调度条件容纳活跃线程块，其余任务随后执行；不能依赖“块 0 一定先完成”这样的假设。

看下面的标量工作分配：

```text
N = 1000 个元素
每块 256 个线程
需要 ceil(1000/256) = 4 个块
实际启动 1024 个逻辑线程，其中 24 个没有对应的有效元素
```

只要核函数在读写前正确检查 `idx<N`，多余线程便不访问数组。这个结论仅针对所描述的标量逻辑，不能直接套用到预读整组数据的向量化版本。

## 4. 最重要的索引公式

```cpp
int idx = blockIdx.x * blockDim.x + threadIdx.x;
```

`blockIdx.x` 表示当前块编号，`blockDim.x` 表示每块在 x 维的线程数，`threadIdx.x` 表示块内编号。它们不是你在 CPU 端传入的普通全局变量，而是设备端可用的 CUDA 内建变量。

例如每块 256 个线程，块 2 的线程 7 负责下标 `2*256+7=519`。在 C/C++ 的零起点索引中，这对应第 520 个元素。

`<<<blocks, threads>>>` 是 CUDA 的启动配置，不是 C++ 模板参数；它还可以写为 `<<<blocks, threads, shared_bytes, stream>>>`。本模块包装的第三项为 0，第四项为 PyTorch 当前流。

## 5. 为什么一定要区分“元素数”和“字节数”？

长度 N 的 FP32 数组通常需要 `N*4` 字节；FP16 数组通常需要 `N*2` 字节。`a.numel()` 得到元素数，而不是字节数。CUDA API 中一些参数以字节为单位，数组下标则以指针所指类型的元素为单位。

`a+1` 对 `float*` 通常前进 4 字节，对 `half*` 前进 2 字节。将 `half*` 重解释为 `float4*` 后，一次类型访问覆盖 16 字节，即八个 half 的存储大小。**重解释地址不等于将数值从 FP16 转成 FP32**；真正转换数值是另一种操作，例如 PyTorch 的 `.float()` 或 `.half()`。

对齐表示地址是某个字节数的整数倍。`float4` 需要 16 字节对齐；一个本来对齐的张量在偏移一个元素后，不一定仍满足宽类型访问的对齐。`is_contiguous()` 描述布局连续性，并不为任意偏移地址提供 16 字节对齐保证。

## 6. 不同内存空间分别做什么？

| 名称 | 初学时怎样理解 | 需要避免的误解 |
| --- | --- | --- |
| 寄存器 | 线程常用的低延迟片上资源 | 更多寄存器不一定更快，可能限制并发驻留资源 |
| 共享内存 | 同一块内协作复用的片上存储 | 数据不会自动在正确时刻准备好，仍需考虑同步 |
| 全局内存/显存 | 容量较大的设备存储，输入输出通常位于这里 | 相邻线程的地址布局会影响访存效率 |
| 本地内存 | 线程私有的地址空间，可能用于溢出的寄存器或局部数组 | “本地”不等于物理上一定在高速片上存储 |
| 主机内存 | CPU 端内存 | 不能直接当作本项目核函数可用的普通设备显存 |

这是简化模型，还没有展开缓存、统一内存、分布式共享内存等主题。先能回答“这份数据属于哪个线程、哪个块、哪个设备”，再学习高级机制。

## 7. 标量、向量化、打包读写

标量版：一个线程处理一个值。`half2` 版：一个线程处理两个 half，`__hadd2` 对两对元素分别相加。`float4` 版：一个线程通过四个分量处理四个 float。`pack128` 版：把 16 字节看成不同类型视图，先搬运再计算。

优化想减少的是某些访存或控制指令等成本，并不是让同一块 GPU 的计算资源凭空翻倍。向量化也引入新的约束：地址对齐、整个数据组有效、最后一块多余线程如何处理。请阅读 [逐元素加法的限制表](../../kernels/elementwise/readme.md)，不要只记住“x8 比 x2 高级”。

## 8. 同步为什么容易让人困惑？

主机启动核函数通常是异步的：CPU 发出任务后可以继续执行，不必逐指令等待 GPU。`torch.cuda.synchronize()` 等待设备上相关工作完成，是主机侧等待的一种方式。`__syncthreads()` 则是设备端线程块内的屏障，两者不是同一个层次。

不要让只有部分线程执行到一个要求全块参与的屏障，然后期待程序正常推进。不同流之间也不会因为写在相邻的 Python 代码里就自动满足全部数据依赖。入门阶段优先使用当前流，不急着人为引入多个流。

本模块的逐元素加法没有跨线程数据依赖，所以不需要为了“保险”随意添加块级屏障。无意义的同步会增加开销，错误的同步还可能造成程序无法继续。

## 9. 如何理解精度和正确性？

FP16、BF16、FP32 的存储格式不同，表示范围和精细程度也不同。浮点数不能表示所有实数，运算顺序可能影响舍入结果；尤其是规约和矩阵乘法，不应把所有比较都设成逐位相等。

当前加法脚本使用最大绝对误差 `<1e-5`。这只是这个测试选择的判据。更一般的测试需要根据算法、dtype、规模和参考结果设置绝对/相对容差，并明确检查非有限结果。不能先放宽容差让所有测试通过，再宣称实现正确。

正确性至少有三层：数学公式是否正确；索引、边界、dtype 和设备是否正确；测试是否真正覆盖了想支持的情况。最后一点常被忽略：几个整齐尺寸通过，并不能证明任意切片和任意奇数长度也安全。

## 10. 怎样读性能测试？

先检查输出再比较耗时。首次即时编译、数据分配、主机设备拷贝、核函数本身的时间是不同组成部分；看清测试究竟测了哪一部分。预热用来减少首次运行因素，重复测量用于观察稳定性，缓存策略也会改变结果。

本仓库当前 `elementwise/test.py` 用 FlashInfer 的计时工具并启用冷 L2 缓存设置，统计 `np.median(times)`。因此原输出的 `mean time` 字样并不准确；中文注释指出这一点但不改变程序输出。

加速比等于基准耗时除以当前耗时。它大于 1 表示这轮更快，小于 1 表示更慢。不要拿不同 GPU、不同尺寸或不同计时设置下的数字当成同条件对比，更不要把核函数更快直接等同于端到端训练/推理一定更快。

## 11. 环境检查与排错顺序

先查驱动与设备，再查 Toolkit 和编译器，再查 PyTorch，最后查额外依赖和当前模块的编译要求。

```bash
nvidia-smi
nvcc --version
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

`nvidia-smi` 显示的 CUDA Version 与本地 `nvcc` 的版本含义不同，不能直接画等号。PyTorch 能执行已有 CUDA 算子，也不意味着系统可以编译新的 `.cu` 扩展。官方扩展工具会用 `nvcc` 处理 CUDA 源码；Ninja、头文件和配套编译器也需要可用。

| 现象 | 优先检查 |
| --- | --- |
| 找不到 `nvcc` | Toolkit 是否安装，PATH 是否正确 |
| PyTorch 的 CUDA 可用性为 False | 是否有可见设备，驱动与 PyTorch 安装是否匹配 |
| `cuda_fp8.h` 不存在 | 当前源码所需头文件与 Toolkit 版本是否匹配 |
| 无法导入 `flashinfer` 或基准函数 | 额外依赖是否安装、版本接口是否与原脚本一致 |
| Unsupported gpu architecture | `nvcc` 是否支持设置的目标架构 |
| 编译内存不足或进程被杀 | 查看构建日志，必要时降低 `MAX_JOBS` 并发数 |
| 执行时报非法访问 | 优先核对 dtype、地址、N、对齐和尾部线程，而非先改编译参数 |

涉及依赖安装时，使用官方版本与平台兼容说明。这里不提供一条声称能适用于全部 GPU 的固定安装命令。

## 12. 学习路线与自测问题

推荐顺序为 [设备查询](../../samples/deviceQuery/readme.md) → `kernels/elementwise` → [激活函数对比](./激活函数对比.md) → `reduce`/`dot_product` → `mat_transpose` → `softmax`/`rmsnorm` → `sgemv`/`sgemm` → 半精度矩阵乘法与注意力。当前基线的模块文档与源码普通自然语言注释已按[进度表](./翻译进度.md)完成中文覆盖；docstring、运行时字符串、原始示例/日志与英文对照按约定保留。中文覆盖不等于全部 GPU 测试通过，请先阅读各模块的实际范围。

每读一个核函数，写下：输入输出形状与 dtype；每个线程、Warp、Block 的分工；数据所在内存空间；边界与对齐条件；同步需求；参考答案和误差；优化相对朴素版减少了什么成本；是否依赖特定架构。

练习一：N=1000、每块 256 线程，共需要多少块？答案 4。最后一个有效下标是 999，而不是 1000。

练习二：一个 `float4` 有多少字节，可容纳多少个 half 的位模式？答案 16 字节、8 个 half；这不是浮点精度转换。

练习三：长度 5 的 half 数组，`idx=4` 满足 `idx<N`，为何不能据此读一个 `half2`？因为还会访问第 6 个元素，即下标 5，已超出有效范围。

练习四：为什么没有 `__syncthreads()` 的向量加法也可以正确？在相互独立且不重叠的输入输出约定下，各线程只写自己的结果，不依赖其他线程的中间数据。

练习五：Python 函数返回后，GPU 是否一定完成？不一定；核启动通常异步，需要在真正消费结果或测量时使用合适的等待与依赖机制。
